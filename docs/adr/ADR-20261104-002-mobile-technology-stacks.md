## 2. Context and Problem Statement

Following the completion of the Next.js web reference stack (Task 007A and Task 007B), the AI Engineering Playbook must establish official standards for mobile application development.

The mobile landscape in TypeScript is dominated by two paradigms:
1. **Bare React Native CLI**: Direct native development where engineers manage `android/` and `ios/` native project files, configure Gradle and CocoaPods manually, and integrate custom C++ TurboModules.
2. **Expo Ecosystem**: Managed workflows where `android/` and `ios/` are ephemeral artifacts generated by `npx expo prebuild`, native modifications occur declaratively via Config Plugins, routing is file-based via `expo-router`, and builds are orchestrated via EAS.

Without a unified architectural model, mobile projects face severe anti-patterns:
- **Duplication & Rule Drift**: Treating React Native and Expo as completely separate silos leads to divergent component guidelines, duplicate lint configurations, and redundant tests.
- **Platform Branching Asymmetry**: AI agents create platform-specific files (e.g. `Picker.ios.tsx`) without the corresponding companion (`Picker.android.tsx`), causing build failures on the opposite platform.
- **Client Bundle Secret Leakage**: Private API tokens or database credentials are inadvertently embedded into Hermes bytecode bundles, easily extracted via static binary analysis.
- **Insecure Token Storage**: Agents default to unencrypted `AsyncStorage` for sensitive credentials rather than hardware-backed secure storage (iOS Keychain and Android Keystore).
- **CI Runner Asymmetry**: Monolithic CI workflows fail because standard Linux runners cannot compile iOS native binaries without expensive macOS runners.

The Playbook requires an architectural standard that supports both bare React Native and managed Expo projects without duplicating core governance or compromising determinism.

## 3. Decision Drivers

- **Constitutional Principle 1 (Human Sovereignty & Separation of Powers)**: Mobile build tools, EAS services, or AI agents cannot waive quality gates or self-approve stage transitions.
- **Constitutional Principle 2 (Architectural Clarity & Explicit Boundaries)**: The boundary between universal cross-platform React code, platform-specific code, and native bridge modules must be strictly defined.
- **Constitutional Principle 3 (Determinism Over Heuristics)**: Verification must rely on deterministic check commands (`tsc`, `eslint`, `jest`, `expo-doctor`, `gradlew`) with reproducible exit codes.
- **Constitutional Principle 4 (Radical Simplicity & YAGNI / DRY)**: Single shared foundation. Core React Native rules must not be duplicated inside Expo stack definitions.
- **Constitutional Principle 5 (Strict Modularity & Technology-Agnostic Core)**: The core governance engine must remain 100% agnostic. All mobile-specific configurations reside in `stacks/`.
- **Constitutional Principle 8 (Uncompromising Quality Gates)**: Mobile checks must prevent secret leaks, unvetted permissions, and untested native code from reaching deployment.

## 4. Considered Alternatives

### Alternative A: Completely Independent Stacks (`react-native` and `expo` Silos)
- *Description*: Maintain `stacks/react-native/` and `stacks/expo/` as two independent, unrelated stacks, each defining its own component rules, linting configurations, and quality gates.
- *Rejection Rationale*:
  - Severe violation of **Principle 4 (Simplicity / DRY)**: Over 70% of mobile rules (React Native primitives, JSX accessibility, TypeScript strictness, Hermes bytecode, secure storage) are identical across both workflows.
  - Causes maintenance desynchronization when core React Native patterns evolve.

### Alternative B: Expo-Only Mobile Stack (Excluding Bare React Native)
- *Description*: Support only Expo and mandate that all mobile projects use Expo managed workflows.
- *Rejection Rationale*:
  - Inflexible: Many enterprise and cryptographic applications require bare React Native CLI for proprietary C++ JSI libraries, custom NDK modules, or brownfield integration into existing native apps.
  - Violates real-world production requirements.

### Alternative C: Layered Two-Tier Hierarchy (React Native Foundation + Expo Extension) [Selected]
- *Description*: Establish a formal Foundation-Extension model:
  - `stacks/react-native/`: The foundational layer establishing cross-platform component standards, TypeScript strictness, platform file routing, Metro configuration, and secure storage invariants.
  - `stacks/expo/`: An extension layer built on top of the React Native foundation, adding `app.json`, file-based routing (`expo-router`), Config Plugins, prebuild mechanics, and EAS boundaries.
- *Justification*:
  - Perfectly adheres to DRY and modularity.
  - Enables bare projects to use `technology_stacks: ["react-native"]` and managed projects to use `technology_stacks: ["react-native", "expo"]`.
  - Guarantees complete architectural uniformity across all mobile projects.

## 5. Decision Outcome

We adopt **Alternative C (Layered Two-Tier Model: React Native Foundation + Expo Extension)**.

### 5.1 The Foundation-Extension Contract
1. **React Native Foundation (`stacks/react-native/`)**:
   - Universal cross-platform primitives (`<View>`, `<Text>`, `<Pressable>`, `<FlatList>`).
   - Platform file companion invariant (`RULE-RN-COMPANION`): Target resolution chains (`.ios` -> `.native` -> base, and `.android` -> `.native` -> base). Standard modules require bilateral resolution across iOS and Android; platform-exclusive modules are exempt if and only if marked with directive pragma AND verified to have platform-guarded imports (`Platform.OS` or `Platform.select`).
   - Storage security policy (`RULE-MOB-SEC-STORAGE`): `AsyncStorage` permitted for non-sensitive UI state and cache. OS-protected secure storage (`react-native-keychain` iOS Keychain / Android Keystore) is the baseline requirement for auth tokens and credentials, with hardware backing utilized where supported by the device. Stage Gate 6 mandates human review of persistence lifecycles.
   - Metro bundler baseline with Hermes bytecode defaults.
2. **Expo Extension (`stacks/expo/`)**:
   - Declares `dependencies: ["react-native"]`.
   - Version policy: Expo SDK 52 (paired with React Native 0.76.3, React 18.3.1, and Expo Router v4) is the initial reference baseline; adopts official $N$ and $N-1$ rolling lifecycle, validated dynamically via `expo-doctor` and `npx expo upgrade`.
   - Workflow taxonomy: Manifest declaration (`manifest.technology_stacks`) is primary and authoritative; package/git introspection serves as fallback evidence. Conflicting configurations halt with `AMBIGUOUS_WORKFLOW_CONFIGURATION` as `INCOMPLETE`.
   - Single source of truth in `app.json` / `app.config.ts`.
   - Declarative Config Plugins (`RULE-EXPO-PLUGINS`): Direct edits to `android/` and `ios/` in Expo projects are barred; drift is caught by `expo-prebuild-check`.
   - File-based routing via `expo-router` under `app/`.
   - OS-protected secure storage via `expo-secure-store` (backed by iOS Keychain / Android Keystore).
   - Signed OTA updates with strict `runtimeVersion` fingerprinting.

### 5.2 Multi-Tier Quality Gate DAG
Quality gates are organized into distinct tiers to balance fast developer feedback with native compilation rigor:
- **Tier 1 (Universal Headless, < 2 min)**: `rn-typecheck`, `rn-lint`, `rn-test` (Jest + RNTL), `rn-companion-check`, `rn-secret-audit`, `expo-doctor`, `expo-config-validate`. Runs on all Linux/macOS runners.
- **Tier 2 (Android Compilation)**: `rn-android-build` (`./gradlew assembleDebug`). Runs on Linux with JDK 17 and Android SDK.
- **Tier 3 (iOS Compilation)**: `rn-ios-build` (`xcodebuild`). Runs on macOS runners for PRs touching native code or release tags.

### 5.3 Mobile Secret Defense Protocol (`SEC-MOB-01`)
- Zero private credentials permitted in mobile bundles.
- All environment variables are treated as public. Only `EXPO_PUBLIC_*` or public configuration keys permitted.
- Automated gate checks scan `.env*` files, source files, and compiled chunks for sensitive keywords (`KEY`, `SECRET`, `TOKEN`, `PASSWORD`, `PRIVATE`, `CREDENTIAL`, `AUTH`).

### 5.4 Segmented Remote CI Architecture
Remote CI pipelines execute in 3 decoupled jobs:
1. `headless-quality-gates` (Ubuntu, fast-feedback).
2. `android-build` (Ubuntu + Android SDK).
3. `ios-build` (macOS runner, conditional).

## 6. Consequences and Trade-offs

### Positive Consequences
- **Zero Duplication**: Core React Native rules are defined once and inherited by Expo.
- **Broad Compatibility**: Supports bare React Native CLI, managed Expo, and prebuild workflows.
- **Cross-Platform Safety**: Companion file enforcement prevents asymmetric iOS/Android breakages.
- **Cost-Effective CI**: Segmented CI avoids wasting expensive macOS runner minutes on universal linting and unit tests.

### Negative Consequences and Trade-offs
- **StackManager Evolution Required**: In Task 007D, `StackManager` must be updated to resolve stack dependencies (`dependencies: string[]`) and support layered template scaffolding.
- **Platform Runner Cost**: Complete verification of iOS native builds still requires access to macOS runners in CI or local developer machines.
